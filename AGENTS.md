# Schematic Converter

An Electron app that converts modern Minecraft schematics to the 1.8.8 `.schematic` format, and has to stay fast on maps with billions of blocks.

## Commands

```sh
npm run dev        # Run the app
npm run typecheck
npm test           # Fast. Run after any engine change
npm run test:e2e   # Builds, then drives the real app. Run after any UI change
npm run format     # Ultracite: formats and applies safe fixes. Run before committing
npm run lint       # Must pass
npm run dist       # Windows installer and portable app, into dist/
```

Set `E2E_EXE` to `dist/win-unpacked/Schematic Converter.exe` to run the end-to-end test against a packaged build. Optional test suites are described in the README.

Terminals inside other Electron apps can inherit `ELECTRON_RUN_AS_NODE=1`, which starts Electron as plain Node. `electron-vite` and the end-to-end test clear it. Anything else that launches Electron has to as well.

## Layout

```
src/engine/       The converter. Plain Node with no Electron imports, so tests can run it directly
  nbt/nbt.ts      Streaming NBT reader, path-based walker, encoder
  convert.ts      One adapter per format, and Job, which they all feed
  decode.ts       The hot loops: varints and Litematica's bit-packed longs
  gzip.ts         Parallel gzip: chunks deflated on libuv's pool, spliced into one stream
  output.ts       Writes .schematic files, including splitting into a grid
  canvas.ts       Paged random-access storage for sources that aren't in file order
  palette.ts      Lookup tables, tile entity position index, report rows
  mapping/        Block, item, tile entity and entity translation to 1.8
  data/           Generated by `npm run generate-data` from minecraft-data. Don't edit by hand
  worker.ts       Entry point of the engine's utility process
  cli.ts          Headless entry point, for benchmarks
src/main/         Window, settings, job queue, engine processes, updater
src/preload/      The narrow API the UI gets
src/renderer/     React UI
src/shared/       Types used across the process boundaries
test/             Vitest suites, the WorldEdit harness, the end-to-end script
scripts/          Data and icon generators, and a big map generator for benchmarks
```

## Formatting and lint

Ultracite on top of Biome. Rules that clash with how this project works are off in `biome.jsonc`, each with its reason, and everything else is meant to pass, so fix what `npm run lint` reports rather than silencing it. Key sorting stays off in `test/`: the order of keys in an NBT fixture is often what the test is testing.

## How a conversion works

Tags in an NBT compound can be in any order, and block data can come before the palette it needs. Each adapter walks the file taking what it can, skips what it isn't ready for, and goes around again if something was skipped. Almost every file finishes in one pass.

Blocks go from gunzip through a palette lookup straight to the output, in file order. `Blocks` and `Data` are generated together but stored one after the other, so each is compressed into its own section. Sections end on a byte boundary, which lets them be spliced into one gzip stream without decompressing. The file's header is a stored deflate block that's patched in at the end, once its values are known. `crc32Combine` joins the checksums.

Sources that aren't in file order (structure files and multi-region litematics) go through `BlockCanvas` first.

## Rules

**Never hold a whole map in memory.** Block arrays must stream. Anything per-block goes in `decode.ts`, with local variables and typed arrays. After changing it, measure with `scripts/make-big-schem.mjs` and `out/main/cli.js`, and compare peak memory as well as time.

**Don't silently lose data.** Anything that can't be read or kept must end up in the report's `warnings` or as an `unmapped` block. An unreadable palette entry turning into air is exactly the failure this rule exists for.

**Test against real files.** Fixtures from our own encoder can't catch wrong assumptions about a format. Minecraft 26.4 renamed palette keys to `id` and `properties`, which only testing real files revealed. For format work, run real samples and the WorldEdit harness.

**Output must load in WorldEdit 6.1.** That's what 1.8.8 servers run. Its reader requires `Materials`, `Blocks`, `Data`, `TileEntities` and `Entities`. `WEOrigin` holds the region's lowest corner and `WEOffset` holds that corner minus the point it was copied from. Entities are in world coordinates and tile entities are relative to the file.

**Don't trust a table without checking it.** minecraft-data's flattening table has wrong entries: wooden trapdoors, levers and comparators, all corrected in `scripts/generate-data.mjs`. Open wooden trapdoors came out closed because of it. Set `FLATTENING_TABLE` to compare with a dump of Mojang's own flattening, and when something is placed wrongly in game, write the test from how 1.8's block class reads its metadata.

**Tile entity ids come from the block being placed**, not the source's id, so a barrel that became a chest gets a working chest. Blocks that keep contents in their state in modern versions (flower pots, note blocks) get their tile entities created from it.

## Adding block mappings

Exact matches come from the flattening table in `data/legacy.json`. Everything newer goes in `mapping/aliases.ts`, as either another block name, which keeps properties so stairs stay stairs, or a fixed `id:meta`. `test/mapping.test.ts` walks every block and state in every version in minecraft-data and fails on anything unmapped. To pick up a new Minecraft version, update the `minecraft-data` dev dependency, run `npm run generate-data`, and fix what the test finds.

## UI

Compact and easy to scan. The look is T3 Code's: its UI font stack, near-black canvas, layered hairline cards and glass. There are no gradients, and the main action is solid white on dark.

- It's a tool, not a chat: no composer or prompt input.
- Everything goes through `components/ui.tsx` and the tokens in `index.css`.
- Show the plain-language result first, with detail one click away.
- Windows 11 draws real glass behind the window, so anything captured from the screen can show the user's desktop through it. Remove `data-glass` from `<html>` before taking screenshots to publish.

## Security

The renderer is sandboxed with context isolation and only reaches the main process through `src/preload/index.ts`. Schematics are untrusted input, so the NBT reader limits depth and buffering, and output names come from the input's file name, never its contents.

## Updates

`src/main/updater.ts` uses electron-updater with GitHub Releases. Installed copies download in the background and install on restart or quit. The portable build can't replace itself, so it opens the release page instead. Nothing happens in unpackaged builds.

Updates only reach people if the release includes `latest.yml` and the blockmap, and if the tag matches the version in `package.json`. Keep the installer's `artifactName` stable.

## Releasing

1. Bump `version` in `package.json`.
2. Run `npm test`, then `npm run dist`, then the end-to-end test with `E2E_EXE`.
3. Publish with `gh release create v<version>`, attaching all four of these from `dist/`: `Schematic-Converter-<version>-Setup.exe`, its `.blockmap`, `latest.yml` and `Schematic-Converter-<version>-Portable.exe`.
